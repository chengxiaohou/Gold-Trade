# 股息率项目：已实现盈亏统计模块 + 本地全量历史存储

## Context（为什么做）

股息率页目前每只股票最多保留 20 条已成交记录（`MAX_FILLED_TRADES=20`），超出的最旧记录被 `compactFilledTrades` 破坏性压成"合并买入/合并卖出"两条汇总并重排到最前。这带来两个问题：

1. **要做"按时间周期统计已实现盈亏 + 逐日明细"时**，合并已把历史逐日信息永久丢失，近一年/近三个月窗口的逐日列表无法还原。
2. **合并本身可能算错**：当一只票累计成交超 20 条且买卖交错时，现有重算逻辑（`calcRealizedPnlMap`）因折叠重排，会让窗口内已实现盈亏与剩余成本价失真。

与用户讨论后的定位：**本地保全量，Gist 同步每只票最新 20 条活记录 + 墓碑（删除 id），交易浮窗显示最新 20 条 + 可展开全量**，全量仅属当前机器、靠 JSON 全量导出/导入备份。全量逐笔历史存 IndexedDB（不撞 localStorage 5MB 墙）。旧数据无需迁移，从功能上线起积累。

**多设备模型（用户敲定）：墓碑 + 软删 + 完全信任云端。** 副设备的增/删/改最终都合并进主设备全量；删除采用软删（`isDeleted`，不真删、不展示），以保住 id 序列稳定、避免对不上错乱。云端除最新 20 条活记录外，每只票另带 `deletedIds`（墓碑，只增，体积小；因删除超出 20 条窗口就无法可靠回传，墓碑是让删除可同步的最小方案）。

最终要交付两个能力：
- A. 存储架构改造：IndexedDB 全量流水账 + Gist 同步层裁剪（墓碑 + 软删 + 信任云端合并，不再破坏性合并）+ 最新20条/展开 + 全量导出导入。
- B. 新的"已实现盈亏统计"模块：快捷周期 + 日历自定义，输出窗口总盈亏 + 逐日买卖明细。

## Step 2：去合并 → 内存全量 + 墓碑/软删 + 信任云端裁剪

1. **移除破坏性合并**：不再调用 `compactFilledTrades`（原 3858-3983 各调用点）在内存里压记录。`MAX_FILLED_TRADES=20` 语义从"数据上限"改为"同步/UI 展示上限"。
2. **软删**：新增成交时保留 `id` 生成逻辑（维持现状）；删除记录不再从数组移除，而是置 `isDeleted=true`（不展示、不计入持仓/盈亏/统计），浮窗删除按钮改为"标记删除/撤销"。`isDeleted` 字段加入 `StockTrade`（可选）。
3. **变更点落库 + 墓碑**：在 4 个交易变更 handler 内取到 final `newTrades` 后：对 `stock.id` 调 `syncLedger(stock.id, newTrades)`，并把"被删记录的 id"并入该股票的 `deletedIds`（墓碑，仅增量），再同步墓碑到 ledger：
   - `handleAddTrade`（L3822）
   - `handleSaveEditTrade`（L3869，明细编辑也经过这里）
   - `handleRemoveTrade`（L3924，改为软删并写墓碑）
   - `handleToggleTrade`（L3947，挂单标记成交）
   相应把这些 `useCallback` 的 deps 补上 `ledgerMap`。为避免整表全量写，写前仅对比该 stockId 的 key，变化才覆盖。
4. **App.tsx 上传裁剪 + 墓碑**：`performStockCloudUpload`（L869-933）构造 `dataToUpload.stocks` 前，对每个 `stock`：
   - 活记录（排除 `isDeleted`）用 `clipToLatest20(trades)`（新增纯函数，放 `services/githubService.ts` 导出：按 `filledAt||createdAt` 降序取前20）；
   - 把该股票 `deletedIds` 一并放进上传 payload。
   云端每只票 = `{ stockTrades: 最新20活记录, deletedIds: [] }`。
5. **App.tsx 下载合并（完全信任云端）**：`handleCloudDownload`（L975-977）收到 Gist 的 stocks 后，对每只股票执行：
   - 用云端 20 条建立 `id → 记录` 表；
   - 以本地 ledger（主设备全量）为基底，遍历云端 20 条：命中的 id → 用云端版本**覆盖**（副设备的修改回传）；未命中的 id → **新增**；
   - 云端 `deletedIds` 中命中、且不在云端 20 条里的 id → 置 `isDeleted=true`（软删回传）；
   - 合并后**按 `filledAt||createdAt` 重排序**，再 `setStocks` 并回写 ledger。
6. **localStorage 持久化不膨胀**：`StockDividendPage.tsx:3106` 的持久化 effect 改为写入时对每只 `stockTrades` 裁剪到最新 20 条活记录（localStorage 只做有界快照），全量交给 IndexedDB ledger。

> 诚实边界（用户已接受，不再实现行级合并）：Gist 整文件覆盖、后上传 wins；同一条并发同改以最后上传者为准。副设备先抢传会覆盖云端，主设备下次"下载合并"时再吸收。

## Step 4：已实现盈亏统计模块

### 计算（新建 `services/realizedPnl.ts`）
`calcRealizedPnlMap`（StockDividendPage.tsx:344）保留不动（兼容 6033/6258）。新增窗口版：
- `calcRealizedPnlForRange(filledTrades, startTs, endTs)`：先扫描 `createdAt < startTs` 的所有成交，算出期初持仓 `rs/rc`（移动加权成本带入窗口）；再扫窗口内 `filledAt||createdAt ∈ [start,end)` 的卖出，`realized = 卖出金额 - rc × 股数`，**归属到该卖出的日期**。
- 返回 `{ total, byDay: Record<'YYYY-MM-DD', { buys[], sells[], dayRealized }>, byStock }`，供"逐日明细 + 总盈亏 + 逐只展开"使用。

### 入口与 UI（复用页面底部"请求统计"栏）
**不新增到列表，直接复用现有底部栏容器**（StockDividendPage.tsx:6689-6840）：
- **切换入口**：新增局部 state `bottomBarView: 'request' | 'profit'`（默认 'request'）。把底部栏最左边的"请求统计"按钮（L6693-6699）改为切换按钮：点击在 `request`/`profit` 之间切换，文案随当前视图显示为"请求统计"/"盈利统计"。

  - `request` 视图：保持现有"请求统计"整段（L6700-6754 的统计数字、L6757-6838 的日志面板展开/导出/重置）原样。
  - `profit` 视图：右侧动作区（导出/重置按钮组）与日志面板替换为盈利统计 UI；仍是**一条可展开的底部栏**——常驻一行汇总（周期快捷切换 + 总已实现盈亏），下方可展开 `max-h-48` 的滚动明细区（复用 L6759 面板样式），展开态由独立的 `showProfitPanel` 控制。
- **周期选择**：6 个快捷 segment（近一周 / 两周 / 近一月 / 近三月 / 近半年 / 近一年）+ 两个 `<input type="date">` 自定义起止；选择结果放常驻行，便于快速换周期。

- **输出（展开明细区）**：顶部"全部股票合计"总已实现盈亏；下方**按天**列当天买卖操作与当天盈亏（默认收起，可展开）；提供"按股票展开"看单只明细。

## 多设备合并规则（下载时，完全信任云端）
对每股股票：
1. 用云端最新 20 条活记录建 `id → 记录` 表；
2. 主设备 ledger（全量）为基底：云端命中的 id → 用云端版本覆盖（**修改回传**）；未命中 → **新增**；
3. 云端 `deletedIds` 命中且不在云端 20 条内 → 置 `isDeleted=true`（**软删回传**）；
4. 合并后按 `filledAt||createdAt` 重排序，`setStocks` 并回写 ledger。
